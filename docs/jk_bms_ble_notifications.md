# JK BMS: почему BLE-уведомления приходили блоками по ~50 штук

## Симптом

При подключении ESP32-C3 к JK BMS через BLE поток данных обрывался ровно
после ~51 уведомления. После паузы можно было запросить новую порцию — и снова
51 уведомление. Официальное приложение JK и ESP32-S3 на Arduino работали
бесконечно.

## Что такое BLE-уведомления и CCCD

В BLE периферийное устройство (BMS) не отправляет данные само по себе.
Центральное устройство (ESP32) должно явно разрешить уведомления, записав
в специальный дескриптор **CCCD** (Client Characteristic Configuration
Descriptor, UUID 0x2902) значение `{0x01, 0x00}`.

CCCD — это двухбайтный регистр, который живёт «рядом» с характеристикой:

```
Сервис 0xFFE0
  └── Характеристика 0xFFE1  (handle 0x0012)  ← сюда пишутся команды
        └── CCCD 0x2902      (handle 0x0013)  ← сюда пишется {0x01,0x00}
```

Запись `{0x01, 0x00}` говорит BMS: «я готов принимать уведомления».

## Первопричина проблемы: порядок операций

JK BMS различает два режима стриминга:

| Режим       | Условие                                      | Поведение              |
|-------------|----------------------------------------------|------------------------|
| Ограниченный | CCCD не записан или записан до команд        | ~51 фрейм, затем стоп  |
| Бесконечный  | CCCD записан **после** команды CMD_GET_INFO  | поток не прерывается   |

Правильная последовательность:
1. Подключиться (BMS пикает — это нормально)
2. Подождать 200 мс, записать CMD_INIT (`0x97`)
3. Подождать 500 мс, записать CMD_GET_INFO (`0x96`)
4. Подождать 1000 мс и **записать CCCD `{0x01, 0x00}` в handle 0x0013**
5. Уведомления идут бесконечно

## Почему мы долго не находили причину

### Версия 1: NimBLE стек
NimBLE (стек BLE по умолчанию для ESP32-C3 в ESP-IDF) записывает CCCD
автоматически при подписке — но делает это **до** отправки команд. BMS
получал CCCD в «неправильный» момент и всё равно ограничивал поток до 51
фрейма.

### Версия 2: гипотеза про MTU
Долгое время казалось, что проблема в MTU. NimBLE согласовывает MTU=131,
тогда как Arduino по умолчанию не вызывает `esp_ble_gatt_set_local_mtu()`,
и мы думали, что BMS ведёт себя иначе при разных MTU. Гипотеза оказалась
ошибочной: оба стека (NimBLE и Bluedroid) согласовывают MTU=131 с этим BMS,
и оба получают 128-байтные фреймы. MTU не влияет на количество фреймов.

### Версия 3: переход на Bluedroid
Мы переписали BLE-слой с NimBLE на Bluedroid (тот же стек, что использует
Arduino). Поток по-прежнему обрывался на ~50 фреймах — это окончательно
исключило стек как причину.

### Решение: CCCD после CMD_GET_INFO
Изучив исходники Arduino BLE библиотеки
(`BLERemoteCharacteristic::registerForNotify`), обнаружили: Arduino
записывает CCCD **после** отправки обеих команд (с задержкой 1 с после
CMD_GET_INFO). Паузы в ESP-IDF коде: 200 / 500 / 1000 мс
(см. `cmd_task` в `bms_ble.c`). Добавили аналогичный шаг в ESP-IDF код — поток стал
бесконечным.

## Итоговый код (упрощённо)

```c
// 1. Найти handle CCCD при обнаружении характеристики
esp_bt_uuid_t cccd_uuid = { .len = ESP_UUID_LEN_16,
                             .uuid.uuid16 = ESP_GATT_UUID_CHAR_CLIENT_CONFIG };
esp_gattc_descr_elem_t descr;
uint16_t count = 1;
esp_ble_gattc_get_descr_by_char_handle(gattc_if, conn_id,
    chr_handle, cccd_uuid, &descr, &count);
// descr.handle == 0x0013 для данного BMS

// 2. В задаче инициализации — после CMD_GET_INFO
vTaskDelay(pdMS_TO_TICKS(200));
esp_ble_gattc_write_char(... CMD_INIT ...);
vTaskDelay(pdMS_TO_TICKS(500));
esp_ble_gattc_write_char(... CMD_GET_INFO ...);
vTaskDelay(pdMS_TO_TICKS(1000));

// 3. Записать CCCD — BMS переходит в режим бесконечного стриминга
uint8_t notify_en[] = {0x01, 0x00};
esp_ble_gattc_write_char_descr(gattc_if, conn_id, cccd_handle,
    2, notify_en, ESP_GATT_WRITE_TYPE_NO_RSP, ESP_GATT_AUTH_REQ_NONE);
```

## Вывод

Поведение JK BMS нестандартно с точки зрения спецификации BLE:
по спецификации CCCD управляет только тем, будет ли периферия
**пытаться** слать уведомления. JK BMS использует момент записи CCCD
как триггер смены внутреннего режима стриминга. Это недокументированное
поведение прошивки конкретного устройства.
