# BMS Web Monitor

Веб-интерфейс для мониторинга и управления аккумуляторной батареей через JK-BMS по BLE.  
Платформа: **ESP32-C3** (одноядерный RISC-V, единый радиомодуль WiFi + BLE).

## Аппаратная часть

| Компонент | Описание |
|---|---|
| MCU | ESP32-C3 (любая плата) |
| GPIO9 | Кнопка BOOT — встроена на всех платах ESP32-C3 |
| GPIO3 (по умолчанию) | Управление реле/транзистором зарядника |
| BLE | Связь с JK-BMS (пассивный скан + GATT-клиент) |
| WiFi | STA / AP / APSTA |

GPIO зарядника и его полярность (`active_high`) настраиваются через веб-интерфейс без перепрошивки.

## Первый запуск

1. Прошейте устройство.
2. На телефоне или ноутбуке найдите WiFi-сеть вида **`BMS-Setup-XXXXXX`** (последние 3 байта MAC).  
   Сеть открытая, пароль не нужен.
3. Подключитесь и откройте **`192.168.4.1`** в браузере.
4. Перейдите на вкладку **«Настройки»**, выберите свою WiFi-сеть, укажите пароль, сохраните.
5. Нажмите **«Перезагрузить устройство»** — устройство подключится к роутеру.
6. Узнайте IP устройства в веб-интерфейсе роутера (или через мDNS, если настроено) и откройте его в браузере.

**Сброс настроек:** удерживайте кнопку BOOT **3 секунды** во время работы прошивки (не во время загрузки!). Устройство сбросит все настройки и уйдёт в режим AP.

## Режимы работы WiFi

Устройство проходит через следующую логику при каждом старте:

```
Старт
 │
 ├─ Есть pending WiFi (новые credentials ожидают проверки)?
 │    ├─ ДА → пробуем подключиться к pending SSID
 │    │        ├─ Успех → pending становится основным, удаляем pending → STA-режим
 │    │        └─ Провал → удаляем pending, продолжаем со старыми credentials
 │    └─ НЕТ → продолжаем
 │
 ├─ Есть сохранённый SSID?
 │    ├─ НЕТ → скан + AP-режим
 │    └─ ДА → пробуем подключиться (15 с, 3 попытки)
 │               ├─ Успех → STA-режим
 │               └─ Провал → скан + APSTA-режим (AP + фоновое переподключение к роутеру)
```

### STA-режим (штатный)

Устройство подключено к домашнему роутеру. Доступно по IP из локальной сети (или через интернет при наличии проброса портов).

- После первого успешного получения IP флаг `s_ever_connected = true`
- При потере связи (роутер перезагрузился, пропал сигнал) STA переподключается **бесконечно** без ограничения попыток — устройство самостоятельно восстановит соединение когда роутер вернётся

### AP-режим (режим настройки, нет сохранённого SSID)

SSID: `BMS-Setup-XXXXXX`, открытая сеть, IP: `192.168.4.1`.

Используется при первом запуске или после сброса настроек.

### APSTA-режим (провал подключения при наличии сохранённых credentials)

Роутер временно недоступен, но credentials сохранены. Устройство одновременно:
- Поднимает AP (`BMS-Setup-XXXXXX`) — для локального доступа и управления
- Пробует подключиться к роутеру в фоне — бесконечно

Когда роутер вернётся, STA-часть подключится автоматически и устройство станет доступным удалённо. AP при этом продолжает работать.

**Ограничение ESP32-C3:** один радиомодуль делится между AP и STA методом time-division. Клиенты AP могут заметить кратковременные (~100 мс) прерывания во время попыток подключения STA. AP и STA работают на одном канале; при подключении STA к роутеру AP автоматически переходит на его канал, из-за чего текущие клиенты AP переподключатся.

### Смена WiFi-сети (двухэтапная фиксация)

Чтобы смена сети не привела к безвозвратной потере доступа при неверном пароле:

1. Пользователь вводит новые SSID/пароль → они сохраняются как **pending** (в NVS-namespace `"wifi_pend"`), основные credentials не меняются
2. После перезагрузки устройство пробует pending
3. **Успех** → pending становится основным (`app_cfg`), pending-запись удаляется
4. **Провал** → pending удаляется, устройство подключается к **старой** сети

Это означает: даже при вводе неверного пароля устройство вернётся на предыдущую сеть и останется доступным удалённо.

## Подключение к BMS

Поддерживается **JK-BMS** (8-канальная, протокол BLE на GATT-сервисе UUID `0xFFE0`, характеристика `0xFFE1`).

### Протокол

1. Passive BLE scan — устройство ищет BDA совпадающий с `cfg->bms_addr`
2. При обнаружении — GATT-подключение
3. Обнаружение сервиса `0xFFE0` и характеристики `0xFFE1`
4. Запись команды `CMD_INIT` (20 байт) → задержка 200 мс
5. Запись команды `CMD_GET_INFO` (20 байт) → задержка 500 мс
6. Запись в CCCD (`0x0100`) для активации notify → начинается стриминг данных

**Критично:** без записи в CCCD стриминг не начнётся (BMS не начнёт слать notify). Без `CMD_GET_INFO` стриминг останавливается примерно через 50 фреймов.

### Парсинг фреймов

Фреймы прибывают в виде BLE notify-пакетов и накапливаются в кольцевом буфере 512 байт. Начало нового фрейма определяется по заголовку `55 AA EB 90`. Фрейм парсится при получении следующего (на длину ≥ 256 байт).

Смещения полей фиксированы (жёстко прошиты в `parse_buffer()`):

| Поле | Смещение |
|---|---|
| `cell_voltage[i]` | 6 + i×2 |
| `cell_resistance[i]` | 80 + i×2 |
| `avg_voltage` | 74 |
| `battery_voltage` | 150 |
| `soc` | 173 |
| `temp1` | 162 |
| `temp2` | 164 |
| `temp_mos` | 254 |
| `cap_remain` | 174 (4 байта LE) |
| `cap_full` | 178 (4 байта LE) |
| `power` | 154 (4 байта LE, signed) |
| `current` | 158 (4 байта LE, signed) |

Если `battery_voltage < 1000` или `> 60000` мВ — фрейм отбрасывается как невалидный.

### Ячейки с нулевым напряжением

BMS 8-канальная, но может использоваться с меньшим числом ячеек. Ячейки с `cell_voltage == 0` считаются неподключёнными:
- В веб-интерфейсе они не отображаются
- В логике зарядки они **пропускаются** при проверке `cell_min_start_mv` и `cell_max_stop_mv`

При подключении новых ячеек они автоматически появятся в интерфейсе и начнут учитываться в логике зарядки.

### Watchdog

`cmd_task` каждые 5 секунд проверяет, что счётчик `s_parse_count` растёт. Если он застыл — значит стриминг прекратился; задача закрывает GATT-соединение. BLE GAP-стек обнаруживает разрыв, возобновляет скан, и при следующем появлении BMS в эфире происходит повторное подключение и инициализация.

### Идентификация JK-BMS в интерфейсе

При BLE-скане устройство считается JK-BMS если:
- В advertisement data есть 16-битный UUID сервиса `0xFFE0`, **или**
- Имя устройства начинается с `"JK-"`

В выпадающем списке выбора BMS устройства JK-BMS выделены в отдельную группу `<optgroup>`.

## Управление зарядкой

### GPIO

Один GPIO-выход управляет реле или транзистором зарядника. Полярность настраивается (`charger_active_high`):
- `true`: HIGH = зарядка включена
- `false`: LOW = зарядка включена

### Условия включения (любое из)

| Параметр | Смысл |
|---|---|
| `soc_start_pct` | SoC упал ниже порога (%) |
| `cell_min_start_mv` | Любая ненулевая ячейка опустилась ниже порога (мВ) |

Если оба параметра равны 0 — автозапуск зарядки отключён полностью.

### Условия отключения (любое из)

| Параметр | Смысл |
|---|---|
| `soc_stop_pct` | SoC достиг или превысил порог (%) |
| `pack_stop_mv` | Суммарное напряжение пакета ≥ порога (мВ) |
| `cell_max_stop_mv` | Любая ненулевая ячейка достигла или превысила порог (мВ) |

### Возобновление после потери питания

Состояние зарядки сохраняется в NVS (namespace `"charge"`, ключ `"in_progress"`). При старте:
- Если флаг = 1 (зарядка шла до отключения питания) → зарядка возобновляется немедленно, не ожидая условия START
- Если флаг = 0 → ожидается условие START (автозапуск)

Это предотвращает ситуацию когда прерванная зарядка не доходит до целевого уровня.

### Ручное управление

Кнопки «Включить»/«Выключить» на вкладке «Мониторинг» вызывают `charge_ctrl_set_override()`. Состояние сохраняется в NVS и переживёт перезагрузку.

### Частота проверки

`charge_task` работает с интервалом 5 секунд. При изменении настроек через веб-интерфейс задача пробуждается немедленно через `xTaskNotifyGive`.

## Авторизация (HTTP Basic Auth)

По умолчанию устройство открыто — авторизация не требуется. Это удобно при первоначальной настройке, но небезопасно при пробросе порта в интернет.

### Включение

Вкладка **«Настройки» → «Доступ»**: поставить галочку «Требовать авторизацию», ввести логин и пароль, нажать «Сохранить». Изменения вступают в силу **немедленно**, без перезагрузки.

- Логин: любое имя пользователя. **Если поле оставить пустым — используется логин `admin`**
- Пароль: произвольная строка. Поле «Новый пароль» при повторном открытии настроек всегда пустое — это нормально. Пустое поле при сохранении означает «не менять пароль». Чтобы сменить пароль — введите новый
- Отключение авторизации: снять галочку и сохранить

### Механизм

Стандартный HTTP Basic Auth (`Authorization: Basic base64(login:password)`). Браузер показывает диалог один раз и затем автоматически подставляет учётные данные на все запросы к устройству, включая SSE и API.

### Забыли пароль

Удерживайте кнопку BOOT **3 секунды** — сбрасываются **все** настройки, включая пароль. Устройство перейдёт в режим AP.

## Веб-интерфейс и API

### Вкладки

- **Мониторинг** — данные BMS в реальном времени (SSE), ручное управление зарядкой
- **Настройки** — WiFi, BMS MAC, пороги зарядки, GPIO, авторизация
- **Логи** — вывод ESP_LOG в реальном времени с инкрементальным поллингом

### HTTP API

Все эндпоинты, кроме `/favicon.ico`, защищены авторизацией если она включена.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/` | HTML-интерфейс (встроен в прошивку) |
| `GET` | `/api/data` | Снимок данных BMS (JSON) |
| `GET` | `/api/events` | SSE-поток, данные BMS каждые 500 мс |
| `GET` | `/api/settings` | Текущие настройки (пароли не возвращаются) |
| `POST` | `/api/settings` | Сохранить настройки (JSON) |
| `POST` | `/api/restart` | Перезагрузить устройство (через 500 мс) |
| `GET` | `/api/wifi/scan` | Список WiFi-сетей (кэш со старта) |
| `GET` | `/api/ble/scan` | Список замеченных BLE-устройств |
| `GET` | `/api/logs?from=N` | Логи начиная с порядкового номера N |
| `POST` | `/api/charger` | `{"on": true/false}` — управление зарядником |

### SSE (Server-Sent Events)

Реализован через async-handler API ESP-IDF: `sse_handler` возвращает управление немедленно, данные рассылает отдельная задача `sse_task`. Поддерживается до **4 одновременных клиентов**. При подключении 5-го клиента вытесняется самый старый (слот 0).

Браузер автоматически переподключается при разрыве SSE (директива `retry: 5000` в первом событии).

### Логи

Кольцевой буфер: 80 записей × 160 символов. Всё что выводит `ESP_LOG*` перехватывается и хранится. ANSI escape-коды вырезаются. API отдаёт записи начиная с указанного порядкового номера (`from=N`), возвращает следующий номер (`next`). Браузер поллит каждые 2 с, накапливая только новые записи.

**Важно:** буфер защищён `portMUX_TYPE` (spinlock), а не мьютексом — это намеренно. Обработчик логов вызывается из любого контекста включая ISR, где мьютекс заблокировался бы и вызвал дедлок.

## Архитектура: модули и зависимости

```
main.c
 ├─ config.c          — NVS: все настройки + pending WiFi
 ├─ wifi_manager.c    — WiFi state machine (STA/AP/APSTA)
 ├─ bms_ble.c         — BLE GATT-клиент + парсинг JK-BMS
 ├─ charge_ctrl.c     — GPIO реле + NVS resume + FreeRTOS task
 └─ web_server.c      — HTTP + SSE + логи
      └─ index.html   — SPA (встроен через EMBED_FILES)
```

### Порядок инициализации в `app_main`

1. `web_server_log_init()` — перехват логов (должен быть первым)
2. `nvs_flash_init()` — NVS нужен для `settings_init` и WiFi
3. `settings_init()` — загрузка конфига из NVS
4. Конфигурация GPIO9 + запуск `boot_monitor_task`
5. `wifi_manager_init()` — блокирует до подключения или таймаута
6. `esp_coex_preference_set(ESP_COEX_PREFER_BT)` — приоритет BT при конкурентном доступе к радио
7. `bms_ble_init()` — запуск BLE-стека и скана
8. `charge_ctrl_init()` — GPIO + resume из NVS + запуск задачи
9. `web_server_start()` — HTTP-сервер

### NVS-пространства имён

| Namespace | Содержимое |
|---|---|
| `"app_cfg"` | Все настройки (`app_config_t`) |
| `"wifi_pend"` | Pending WiFi credentials (временно, до проверки) |
| `"charge"` | Флаг `in_progress` контроллера зарядки |

## Нюансы для разработчика

### HTTP Basic Auth — пустой логин и логин "admin" равнозначны

В `check_auth()` используется: `want_user = cfg->auth_user[0] ? cfg->auth_user : "admin"`. Если поле логина в настройках пустое, подставляется `"admin"`. Явно написать `"admin"` и оставить поле пустым — одно и то же. Это сделано чтобы пользователь мог не заполнять логин и запомнить только пароль.

Авторизация применяется ко всем эндпоинтам кроме `/favicon.ico`. `auth_pass` из `GET /api/settings` не возвращается; `auth_user` — возвращается. При `auth_enabled = false` в `POST /api/settings` оба поля `auth_user` и `auth_pass` в `app_config_t` очищаются, и `check_auth` начинает пропускать всех без проверки.

### Кнопка BOOT (GPIO9) — нельзя проверять при старте

GPIO9 на ESP32-C3 — **strapping pin**. Если удерживать его LOW во время снятия RESET, чип уходит в режим загрузчика (DL mode) и прошивка вообще не запускается. Поэтому проверку BOOT нельзя делать в начале `app_main`. Вместо этого используется задача `boot_monitor_task`, которая поллит GPIO9 каждые 100 мс **во время работы** прошивки.

### BLE + WiFi коэксистенция

ESP32-C3 имеет один радиомодуль. BLE и WiFi делят его через аппаратный арбитр. Вызов `esp_coex_preference_set(ESP_COEX_PREFER_BT)` отдаёт предпочтение BT при конфликтах. Без этого данные BMS могут приходить нерегулярно при активном WiFi-трафике.

### Парсинг BMS — фиксированные смещения

Смещения байт в фрейме JK-BMS захардкожены в `parse_buffer()`. Если производитель изменит формат в новой прошивке BMS, все поля сдвинутся. При добавлении поддержки другой версии протокола — проверьте смещения логическим анализатором или сравнением с официальным приложением.

### HTML встроен в прошивку

`index.html` включается через механизм `EMBED_FILES` в `CMakeLists.txt`. Линкер создаёт символы `_binary_index_html_start` и `_binary_index_html_end`. При изменении HTML нужна **полная пересборка и перепрошивка** — отдельно обновить файл не получится. Если нужна возможность обновлять HTML без перепрошивки, можно перейти на SPIFFS/LittleFS, но это усложняет деплой.

### Размер буфера JSON в SSE

`bms_data_to_json()` пишет в буфер 680 байт, финальная строка `"data: ...\n\n"` — 700 байт. Если добавляете новые поля в JSON — проверяйте что буферы достаточны. `snprintf` молча обрежет строку без сигнала об ошибке.

### Мьютекс vs. spinlock в логах

`web_server.c` использует `portMUX_TYPE` + `portENTER_CRITICAL` для буфера логов — **не** обычный мьютекс FreeRTOS. Это принципиально: `esp_log_set_vprintf` вызывается из любого контекста (включая прерывания и callback'и Bluedroid), где мьютекс заблокировался бы. Spinlock безопасен в любом контексте, но не должен удерживаться долго. Текущий код копирует одну запись под локом — это нормально.

### Лимит одновременных HTTP-соединений

ESP-IDF httpd настроен на `max_open_sockets = 7`. Из них одно занимает SSE (длинное соединение). При 4 SSE-клиентах остаётся 3 слота для обычных запросов. Если браузер открывает несколько вкладок или делает параллельные запросы — можно упереться в лимит. При нехватке включён `lru_purge_enable`, который закрывает самое давнее неактивное соединение.

### Смена WiFi — pending credentials

Когда пользователь меняет SSID в настройках, новые данные НЕ пишутся сразу в `app_cfg.wifi_ssid/wifi_pass`. Они сохраняются в NVS-namespace `"wifi_pend"`. При следующей загрузке `wifi_manager_init()` пробует pending первым. Если вы добавляете логику работы с WiFi credentials — учитывайте оба места хранения.

### APSTA режим и канал WiFi

При APSTA (AP + STA одновременно) оба интерфейса должны работать на одном канале. Если STA подключается к роутеру на канале 6, AP автоматически переходит на канал 6. Клиенты AP при этом переподключатся. Это ограничение железа ESP32-C3, обойти его нельзя.

### `any_start_configured()` — только для IDLE

Проверка "задано ли хоть одно условие старта" выполняется только в состоянии `CHARGE_STATE_IDLE`. В состоянии `CHARGE_STATE_CHARGING` она не применяется — намеренно. Иначе если пользователь очистит все условия пока идёт зарядка (возобновлённая после потери питания), зарядка немедленно остановится несмотря на активный NVS-флаг.

### `s_ever_connected` и `s_sta_bg_reconnect`

Два разных механизма бесконечного переподключения:
- `s_ever_connected = true` — когда устройство хотя бы раз получило IP. После этого при любом разрыве STA переподключается без ограничения попыток.
- `s_sta_bg_reconnect = true` — когда AP поднята с сохранёнными credentials (APSTA). STA в фоне пробует роутер бесконечно. Флаг выставляется в `start_ap()` и никогда не снимается (сброс только при перезагрузке).

### Сборка ESP-IDF

Проект собирается с **ESP-IDF v6.0**. Если версия другая — возможны проблемы с API `httpd_req_async_handler_begin` (появился в IDF 4.4+) и `esp_coex_preference_set`. Перед обновлением IDF проверьте changelog по этим функциям.

## Сборка и прошивка

```bash
# Инициализация окружения
source ~/esp-idf/export.sh

# Сборка
cd /path/to/project
idf.py build

# Прошивка
idf.py -p /dev/ttyUSB0 flash

# Мониторинг UART (115200 бод)
idf.py -p /dev/ttyUSB0 monitor

# Сброс в bootloader для прошивки без кнопки
idf.py -p /dev/ttyUSB0 flash monitor
```

### Разделы flash (partition table)

Используется кастомный `partitions.csv`. Раздел приложения — 3 МБ, занято ~1.4 МБ (54% свободно). NVS — стандартный раздел 0x6000 байт.
